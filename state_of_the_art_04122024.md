# REMIX Challenges and Limitations

## Introduction

Remix IDE is a popular, no-setup, browser-based development tool with a user-friendly interface for smart contract development. It’s highly regarded for its simplicity, rapid deployment capabilities, and integration with EVM-based chains. However, its utility diminishes when working with non-EVM-based blockchains. This article explores the challenges and limitations of using Remix for AssetHub with Pallet-Revive on the Westend network.

---

## Strengths of Remix IDE

Remix has several standout features that make it a preferred choice for prototyping in EVM-based development:

### GUI and Ease of Use

Remix allows developers to quickly start building and deploying smart contracts with minimal setup.

### Plugin-Based Architecture

Everything in Remix is a plugin. Core plugins handle essential tasks, while additional plugins extend functionality, creating a modular ecosystem.

### Portability

As a static webpage, Remix can be easily hosted on platforms like GitHub Pages. For example, https://remix.polkadot.io is hosted on GitHub Pages and is built from our [remix-project fork](https://github.com/paritytech/revive-remix/tree/release-0.54.0-dev). This approach makes deployment both accessible and flexible.
Additionally, Remix can be compiled into a desktop application, providing access to the local filesystem.

### Feature-Rich Environment

- Visual debugger for smart contracts. 
- Support for multiple solc compiler releases.
- Seamless deployment to EVM-compatible chains.  
- Integration with MetaMask for network interaction.  
- Solidity static analysis tools for error checking.
- Unit tests support.
- DApp generator.

## Challenges of Adapting Remix for the AssetHub Chain

While Remix excels in Ethereum development, adapting it for other blockchains, like AssetHub with Pallet-Revive, faces significant obstacles:

### 1. Custom Compiler Integration  

Pallet-Revive executes PVM bytecode, generated by the Revive compiler. Unlike Ethereum’s soljson Solidity compiler with its solc-js JavaScript wrapper, Revive is a native binary, requiring [backend](https://github.com/paritytech/revive-remix-backend) integration for Remix compatibility.
Future plans include replacing this backend with a WASM cross-compiled Revive compiler for better integration. The first compiler release as WASM is available here: [Revive v0.1.0-dev.6](https://github.com/paritytech/revive/releases/tag/v0.1.0-dev.6).  

### 2. Bytecode Differences

Polkadot Virtual Machine (PVM) bytecode is incompatible with Remix's built-in VM/Simulator. This requires a Revive-pallet-based simulator for local deployment, debugging, and unit testing.

### 3. RPC Node Compatibility

Pallet-Revive’s proxy server, which emulates Ethereum JSON-RPC, lacks full compatibility with the Ethereum standard, leading to issues with Remix's transaction handling.

### 4. Currency and Token Handling

Remix is Ethereum-centric and doesn’t natively support non-ETH tokens. For the AssetHub chain on the Westend network, where WND tokens are used, custom functionality must be implemented.

### 5. Testing and Debugging

Remix’s built-in simulator relies on [EthereumJS](https://github.com/ethereumjs/ethereumjs-monorepo) components. Developing a Revive-pallet-based simulator is essential for local contract testing and debugging.  

Workarounds to redirect Solidity unit tests to the Westend network partially address the issue, but they are not functional due to missing deploy-time linking support in Revive: [Revive Issue #91](https://github.com/paritytech/revive/issues/91).
Additionally, debugging functionality is lacking.

### 6. Plugin Dependency

Remix heavily relies on Ethereum-specific tools like Etherscan integration. These tools lack compatibility with Pallet-Revive, necessitating replacements or new integrations.

## Approach Options  

### **Option 1: Plugin Development**

Create a custom plugin to bridge the gaps, handling tasks such as:  
- Compilation using Revive.  
- Running and deploying transactions.  
- Solidity unit testing and debugging on an internal VM.  

**Pros**: Modular and easier to maintain within the Remix ecosystem.  
**Cons**: The required modifications essentially create a “sub-IDE” within Remix. At this point, building a dedicated IDE might be more efficient.  

### **Option 2: Forking Remix (Our Current Approach)**

Fork Remix and introduce all necessary modifications directly into the codebase. Currently, most core plugins—such as development, deployment, Solidity unit testing, and the compiler—are modified, while others, like the file explorer and Solidity static analysis plugins, remain untouched.

**Pros**: Quick implementation to meet immediate needs.  
**Cons**: High maintenance cost, as the current fork (based on Remix v0.54) lags behind the main branch, which has seen over 100 pull requests and seven releases since August. Keeping the fork up-to-date is labor-intensive.

### **Option 3: Contribute to Remix**

Make the changes universal around the core plugins and propose them as contributions to the Remix project.  

**Cons**: Remix’s Ethereum focus may limit the acceptance of non-Ethereum-centric contributions.  

---

## Ongoing Development and To-Do List  

Regardless of the approach, the following tasks need to be addressed:  

### **1. JS/WASM Compiler Integration**

Switching from a native backend to a WASM-based Revive compiler is in progress. This will simplify integration and reduce reliance on external servers.

### **2. Simulator Development**

A Revive-pallet-based simulator is essential for robust in-browser contract testing and debugging. Current tests rely on the Westend network or a test node like KitchenSink, which isn’t ideal for iterative development.

### **3. PVM Debugger**

The debugging functionality requires the implementation of instruction-level tracing, which allows tracking each individual instruction being executed and provides visibility into the execution flow. Additionally, state inspection is needed to enable developers to view the state of the virtual machine, including registers, memory and the chain storage, at any point during execution.

### **4. E2E Remix Tests**

Current modifications are not covered by the Remix E2E tests. Running them will require significant effort.

### **5. Remix Desktop**  

As mentioned, Remix can also be built as a desktop application. Remix Desktop, an Electron-based version of the Remix IDE, is compatible with Linux, Windows, and macOS. However, further modifications are needed to make it compatible with our current approach.

### **6. Remix Issues**

These issues are not specific to our changes but exist in Remix and likely require attention:  
- Remix struggles with handling simultaneous requests, such as sending multiple transactions without waiting for prior results. This can lead to system hangs.  
- Switching between networks during development can cause Remix to hang.

---

## Conclusion

While Remix IDE is a formidable tool for Ethereum development, adapting it for custom blockchain ecosystems like Pallet-Revive involves significant compromises. The decision to use Remix boils down to balancing short-term convenience with long-term sustainability.  

For Pallet-Revive, the extensive customizations required—whether through plugins or a fork—may justify developing a purpose-built IDE. Contributing back to Remix could provide some relief, but its Ethereum focus might limit its viability.  

Ultimately, Remix’s Ethereum-centric design makes it a powerful IDE for its intended audience, but it may not be the best option for ecosystems with fundamentally different architectures.
